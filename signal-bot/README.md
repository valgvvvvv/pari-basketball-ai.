# Сигнал

Отдельный бот, читающий карточки `#priorityForecasts .priority-card` на https://pari-basketball-ai.onrender.com/. Использует расчёт и фильтры самого сайта. Не рассчитывает свои вероятности, не отправляет ставки букмекеру.

Chromium держит сайт открытым в фоне; сайт обновляет LIVE каждые 30 секунд, бот проверяет верхний блок каждые 5 секунд. Получение сигнала зависит от доступности сайта, Telegram и источников. Скрытые и просроченные карточки пропускаются. Одна комбинация события, цели, четверти, линии и направления отправляется один раз, включая перезапуски. Изменение только процента не вызывает повтор. Изменение линии или направления создаёт новый сигнал. При аварии непосредственно после отправки до записи в SQLite возможен повтор.

Конфигурация: `../data/signal-bot.json` с полями `token` и `chat_id`; файл исключён из Git. Состояние: `../data/signal-bot.sqlite3`. Не использовать токен другого бота. Не запускать две копии одновременно.

Установка: `python -m venv signal-bot/.venv`, затем `signal-bot/.venv/Scripts/python -m pip install -r signal-bot/requirements.txt` и `signal-bot/.venv/Scripts/python -m playwright install chromium`. Запуск: `Start-Signal.ps1`. На Windows работает, пока включён компьютер и процесс.

Команды владельца: `/status`, `/pause`, `/resume`, `/start`. Остальные чаты игнорируются.

## Облачный запуск

Контекст Docker-сборки — папка `signal-bot`, Dockerfile копирует только код и requirements. На сервере задаются секреты `SIGNAL_BOT_TOKEN` и `SIGNAL_CHAT_ID`. `SIGNAL_DATA_DIR=/app/data` указывает постоянный том для SQLite. JSON-конфигурация с компьютера в образ не попадает. Chromium требует больше ресурсов, чем обычный Telegram webhook.

`render.yaml` описывает отдельный фоновый worker Starter и постоянный диск 1 GB; это платная конфигурация, применять только после согласования стоимости. `compose.yaml` подходит для существующего Linux VPS с Docker. Повторное создание браузера после нескольких ошибок обеспечивает восстановление после его падения.

Перед запуском облачного экземпляра остановить локальный процесс. Согласованную SQLite-копию переносить через `sqlite3.Connection.backup`, не копировать активную WAL-базу как обычный файл. После переноса проверить `/status`, получение новой карточки, сохранение состояния после перезапуска. Только после этих проверок считать перенос завершённым. Не запускать два экземпляра одновременно.

## Бесплатный запуск GitHub Actions

`signal-detector.yml` следует разместить в `.github/workflows/` на основной ветке публичного репозитория. Стандартный Ubuntu runner проверяет сайт каждые 5 минут с возможными задержками GitHub. Бот открывает тот же сайт и читает тот же детектор. Карточки, появившиеся и исчезнувшие между проверками, могут быть пропущены. Команды Telegram обрабатываются во время очередного запуска, ответ может прийти через несколько минут.

Токен и ID владельца задаются только в Actions Secrets (`SIGNAL_BOT_TOKEN`, `SIGNAL_CHAT_ID`). Не записывать их в YAML, исходники или журналы. `SIGNAL_INITIAL_STATE` — необязательный JSON с предыдущими ключами отправленных сигналов и offset команд для переноса с компьютера.

История отправок хранится в Actions Cache, который может быть вытеснен или удалён. Поэтому постоянство истории не гарантируется. При отсутствии кэша первая успешная проверка запоминает текущие карточки без отправки; последующие проверки отправляют новые направления. Локальная история и служебные данные команд при переносе не загружаются. Месячная плата за новый сервер не требуется; применяются ограничения GitHub Actions и сайта. После 60 дней отсутствия активности в публичном репозитории GitHub может отключить расписание.
